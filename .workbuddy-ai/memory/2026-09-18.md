### H1 fixed — the catalog probe no longer crashes the app on startup

`fetchHermesAcpModels` spawned raw (`hermes.ts:344`) and wrote to `child.stdin`
with a completion callback but **no stream `'error'` listener**. Node invokes
the callback *and* emits `'error'` on the stream, and an unlistened stream error
is an uncaught exception. The probe runs at instance create — so that crash
landed on the user's launch. `procs.ts:87` documents and guards exactly this in
`spawnCli`; the probe spawned raw and bypassed the guard. Now
`child.stdin?.on("error", () => done([]))` at `hermes.ts:385`.

Reproduced **before** fixing, which is the part that makes it a proof. The test
(`hermes.test.ts` → `fetchHermesAcpModels stdin safety`) has the fake ACP child
call `closeSync(0)` and *then* answer `initialize`, so the probe's next write
(`session/new`) lands on a closed pipe. Closing fd 0 is synchronous and precedes
the reply, so the failing write is guaranteed rather than raced — the usual way
a test like this would go flaky.

**The trap worth remembering:** asserting that the probe resolves proves
nothing here. The write callback settles the probe either way, so
`resolves.toEqual([])` passes against the *broken* code — vitest reported the
EPIPE as a separate unhandled error and still showed the test as ✓. The test
now installs its own `process.on("uncaughtException")` listener and asserts it
was never called. Pre-fix that fails with
`expected [ Error: write EPIPE ] to deeply equal []`; post-fix 55/55.

### Item W1/H2 — `session/prompt` had no deadline

`core.ts` called `request("session/prompt", …)` with no `timeoutMs`, and
`request` only arms a timer when one is passed. A child that stalls without
exiting — hung tool, network stall — left the turn active forever, because
`active` is cleared only in `settle`. Every later `sendTurn` on that thread then
threw `"a turn is already running"`, and only a manual interrupt recovered.

**The fix is an idle watchdog, deliberately not a fixed `request` timeout.**
A one-shot `timeoutMs` would be armed once and would kill a healthy long turn (a
build, a slow tool) — that is the opposite of the owner's "must not perform
poorly" goal. The watchdog:

- arms when `state.promptSent = true` — the point after which nothing else in the
  turn can settle it;
- is re-armed by **every decoded inbound frame**, so a turn that keeps streaming
  is never cut off no matter how long it runs;
- **stands down while a permission ask is open** (`asks.size > 0`) — that wait is
  the user's, not the agent's — and is re-armed when the ask resolves;
- is cleared in `settle` beside `interruptTimer`;
- fires as `runtime.error` + `settle(false, "prompt_timeout")`, which clears
  `active` and so actually un-wedges the thread.

Default **600 s**; `DANI_ACP_PROMPT_IDLE_TIMEOUT_MS` overrides it and is read
**per turn, not at module load** — the existing timeout constants are read at
import, which makes them untestable, so this one is a function. `<= 0` disables.

Files: `server/drivers/acp/core.ts` (watchdog + 4 call sites),
`server/drivers/acp/acp.test.ts` (2 tests), `server/testing/fake-acp-cli.ts`
(new `drip` mode).

### Reproduced before fixing — the part that makes it a proof

New test `acp.test.ts` → "a stalled prompt is settled by the idle watchdog
instead of wedging the thread": `FAKE_ACP_MODE=hang` never answers
`session/prompt`, window shortened to 150 ms.

- **before:** `Error: no matching event within 5000ms; saw: turn.started,
  session.started` — no `turn.completed` ever arrives. That *is* H2: the thread
  is wedged, and the 5 s figure is only the test's ceiling.
- **after:** `Tests 2 passed (2)`.

The test also asserts the wedge is gone rather than merely reported:
`hasSession` is false afterwards, and a second `sendTurn` on the same thread
completes.

### A second test that proves the other direction, and an honest caveat

`drip` is a new fake mode that streams a chunk every `FAKE_ACP_DRIP_GAP_MS` for
`FAKE_ACP_DRIP_CHUNKS` chunks, so a turn can outlive the idle window while
staying alive. "a slow but chatty prompt is not cut off by the idle watchdog"
runs ~480 ms of output against a 150 ms window and expects `ok: true`.

**Caveat recorded in the doc:** that second test passes with *and* without the
fix by construction (before the fix there is no watchdog at all), so it is a
regression guard, not a reproduction. It must not be cited as the proof — only
the first test is.

The audit said Hermes-spawned MCP children "can survive" the probe. That is a

probe's env. **That objection is now answered** rather than worked around —
`spawnCli` takes an optional 4th `resolveEnv`, so the probe keeps its env-based
resolution and gains its own process group. Its stderr also moved from `ignore`
to a drained pipe, because `spawnCli`'s contract is three pipes and an undrained
one would let a chatty agent block the handshake.

### Item: MEDIUM "unbounded buffers" — the last MEDIUM finding

Two accumulators, both uncapped: the stdout line buffer (`core.ts:977`,
`let buf = ""`) and the turn text (`state.text`). stderr was already capped at
8192, so the pattern was known and simply not applied here.

Fixed with two **per-turn-read functions**, not module constants — the trap
recorded in gauntlet §5:

- `DANI_ACP_MAX_FRAME_CHARS` (16 MiB), read through a new `positiveEnvOr` that
  falls back on a non-positive value rather than letting a typo disable the limit.
- `DANI_ACP_MAX_TURN_TEXT_CHARS` (4,000,000).

The frame cap is deliberately generous: ACP frames legitimately carry whole
inline base64 images in a single `agent_message_chunk`.

### The half that is easy to get wrong

**The cap can only fire on an *unterminated* frame.** A frame that arrives with
its newline is consumed by the line loop *before* the cap is consulted — so when
the cap fires, the decoder is always holding a frame whose end it has not seen.
The fix therefore enters a `discardingFrame` state and skips to the next newline.
Clearing the buffer and resuming would re-accumulate the rest of the same
oversized frame, which is exactly the growth the cap exists to stop; splicing its
tail onto the following message would lose that message instead.

Truncated text is not silently shortened: the flush appends
`[This reply was cut off at N characters.]`, because a reply that just stops
reads as the agent having failed rather than as a limit being hit.

### Reproduced before fixing — including a trap in the fake

Two new fake modes, `oversize-frame` and `flood-text`.

- "drops an over-cap frame, then reads the message that follows it" — pre-fix
  `expected [] to have a length of 1`: no drop ever happened.
- "bounds the assistant text one turn will hold, and says it was cut" — pre-fix
  the item was 5000 `y`s with no marker.

Reproduction was run by stashing **only** `core.ts` (keeping the test and the
fake), which is the cleanest way to show the test fails for the right reason.

The trap: `oversize-frame`'s 40 ms pause is load-bearing, not politeness. Written
without it, the oversized bytes and their newline arrive in one chunk, the line
loop eats the line before the cap is consulted, the cap never fires, and the test
passes while proving nothing. That is the **second** time this loop has produced
a test that could not fail; both times the fix was to make the fixture model
reality rather than to weaken the assertion.

### Item: W1/H4 run A — hoist the per-turn message loop into an explicit session

The queue's last instruction was explicit: take run A only, do **not** attempt
the cache in the same run. So the deliverable is a seam, not a speed-up.

`sendTurn` was a single ~800-line closure holding two different lifetimes at
once: the **session** (child process, JSON-RPC id space, `rpcPending`, stdout
line decoder + `discardingFrame` resync state, native `sessionId`,
`sessionConfigResult`, and the frame-routing handlers) and the **turn**
(`turn`/`turnConfig`/`cliTurn`, `controlsHost`, `state`, `asks`, the idle
watchdog and interrupt timers, `maxTurnTextChars`/`maxFrameChars`). Both were
captured as constants, so nothing could outlive a turn.

Now: `createSession(...)` (`core.ts:543`) owns the session half and exposes
`{ stop, interrupt, startTurn }`; an `AcpTurn` object (`core.ts:515`) owns the
turn half; the session reads it through `owner` (`core.ts:554`). `sendTurn` is
reduced to provider prep → spawn → build `owner` → `createSession` → register in
`active` → `emit turn.started` → `session.startTurn()`.

**The indirection is the entire point.** Because the loop reads `owner.threadId`,
`owner.state.promptSent`, `owner.asks.size` etc. rather than closing over
constants, run B can adopt an existing session by reassigning `owner` and
branching inside `startTurn` — and will not have to touch the decoder, the
permission broker, or `settle`. That was the risk the run-3 scope note
identified, and it is now removed from run B's path.

### Deliberately unchanged

- The session is still created **per turn** and `settle` still calls `stop()`, so
  the audit's "children are per-turn and always reaped by `killCliTree`" still
  holds. Run A does not weaken a security property.
- `active.set(threadId, { stop: session.stop, ... })` — the registry now reaches
  the child through the session, but the object it stores is the same shape.
- `MAX_TURN_TEXT_CHARS()` / `MAX_FRAME_CHARS()` are still read per turn (now when
  `owner` is built, still immediately after spawn).

### Coverage added, and why

`stopAll` had **no test at all** — and it is exactly the wiring a session/active
split breaks (the registry must hold the session's `stop`, not a per-turn
closure). New test in `acp.test.ts`: kill a hung turn's child through `stopAll`,
assert the settle that must follow (`exit_before_result`), assert `hasSession`
is false.

**Proved it can fail**, because this loop has twice shipped a test that could
not: with the wiring broken on purpose (`stop: () => {}`) it fails with
`no matching event within 5000ms; saw: turn.started, session.started` — the
child outlived the turn.

That experiment left an **orphaned `fake-acp-cli` process** behind (pid 42249,
reparented to launchd), which is itself the leak the test describes. Killed and
confirmed clean. Worth remembering as a technique: the stray process is
independent corroboration that the assertion targets the real failure mode.

rather than a set of constants baked into a closure. A refactor with no
behaviour change is still the right unit of work when the alternative is a cache
keyed on something that varies.
